# Ревью проектного документа «Плагин Halation для Photoshop» (v3)

- **Дата:** 2026-11-21
- **Предмет:** `docs/superpowers/specs/2026-11-21-halation-plugin-design.md`
- **Рецензент:** независимый (Fable), документ не редактировался
- **Как проверялось:** чтение документа и обоих исследований; численные проверки на Node 24 (в том числе `node --jitless`, Apple M2 Pro). Photoshop не запускался, поэтому всё, что касается поведения Imaging API, проверено только по исследованию.
- **Итог:** 3 блокера, 8 существенных замечаний, 10 мелких. Физическая модель и коэффициенты в целом верны; основные проблемы — в правиле выбора уровня пирамиды, в обратном переводе для своей кривой, в предпросмотре для режима 2 и в целях по скорости.

## Что подтверждено проверкой (менять не нужно)

- **Коэффициенты экспоненты через гауссианы подходят именно для 2D-радиального профиля.** Σα·β² = 2.988 (для 2D-экспоненты нужно 3, для 1D — 2). Максимальное отклонение кумулятивной энергии от `1 − (1 + R/λ)·e^(−R/λ)` — 1.3 % (при R ≈ 1.9λ), критерий 2 % из 5.3 выполнен. Если те же числа прочитать как 1D-профиль, отклонение 10.9 %, то есть применять их можно только как сумму двумерных изотропных гауссиан. Подгонка не нужна.
- **Модель `O_c = (L_c + a_c·H_c)/(1 + a_c)`** — выпуклая комбинация при `K ≥ 0, ∫K = 1`: ровное поле неизменно, результат не превышает максимум входа, однородность первой степени (умножение света на s умножает выход на s) выполняется точно.
- **Цвет по умолчанию:** sRGB (255, 144, 39) → линейно (1, 0.279, 0.020). Сходится.
- **Таблица √L на 4096 точек для стандартной sRGB:** максимальная ошибка 0.0002 ступени. Для sRGB претензий нет (для своей кривой — см. Б2).
- **Начальная кривая режима 2:** монотонный сплайн по 12 внутренним точкам приближает sRGB с относительной ошибкой линейного значения до 0.5 %. Достаточно.

## Блокеры

### Б1. Правило выбора уровня пирамиды требует полноразмерных float-буферов и не определено для σ < 2 px

**Раздел:** 5.6 п. 2, 5.7, 6.1 (предпросмотр), 3 (память).

**Проблема.** Правило «самый грубый уровень, где σ ≥ 2 px» при значениях по умолчанию отправляет часть гауссиан на уровень 0 (полное разрешение). Это противоречит «полноразмерных float-буферов быть не должно» и цели «60 Мп — не больше ~500 МБ». Для σ < 2 px на уровне 0 правило вообще не даёт ответа, а три box-прохода при σ < 1 px невозможны (ширина окна меньше 1 пикселя).

**Доказательство** (σ в пикселях полного разрешения, `λ₁ = 0.0018·длинная·m`, шесть гауссиан на канал):

| Длинная сторона, m | Гауссианы, попавшие на уровень 0 | Из них σ < 2 px |
|---|---|---|
| 6000, ×1 | G: 3.18; B: 2.03 | 0 |
| 9504 (60 Мп), ×1 | B: 3.21 | 0 |
| 6000, ×0.25 | R: 1.45; G: 0.80, 2.26, 2.63; B: 0.51, 1.44, 2.62, 1.67 | 5 |
| 500 (предпросмотр), ×1 | 13 из 18 | 11 (минимум 0.17 px) |

- На 60 Мп одна гауссиана синего на уровне 0 — это float32-плоскость 240 МБ плюс рабочий буфер box-фильтра 240 МБ. Лимит превышен ради слагаемого с весом `a_B·0.6·0.163 ≈ 0.0014·0.098 ≈ 1.4·10⁻⁴` от L.
- По замеру в `node --jitless` одна гауссиана (3 box-прохода по обеим осям) стоит около 340 нс на пиксель: на уровне 0 для 24 Мп — около 8 с на каждую.
- В предпросмотре (500 px) 11 из 18 гауссиан имеют σ < 2 px. Без точного правила для малых σ предпросмотр и результат разойдутся — это анти-цель из раздела 2.

**Предлагаемая замена текста 5.6 п. 2–3:**

> 2. **Базовая сетка.** При применении — уровень 1 (половинное разрешение); в предпросмотре — сама уменьшенная копия. Ниже базовой сетки размытие не считается, полноразмерных float-буферов нет.
>    - Гауссиана считается на самом грубом уровне, где её σ ≥ 2 px этого уровня, но не ниже базовой сетки.
>    - Если на базовой сетке σ < 2 px, используется прямая раздельная свёртка с дискретным гауссовым ядром: веса — интеграл гауссианы по пикселю (через erf), сумма весов равна 1, радиус окна ⌈3σ⌉.
>    - Если на базовой сетке σ < 0.3 px, гауссиана заменяется дельтой: её вес прибавляется к `L_c` без размытия.
> 3. **Сборка `H_c` сверху вниз.** Результат уровня k+1 билинейно увеличивается вдвое и прибавляется к уровню k, и так до базовой сетки. Во втором проходе по полосам остаётся одно увеличение ×2 с постоянными весами 0.75 / 0.25.

Сборка сверху вниз заодно убирает прямое билинейное увеличение с уровня 5–8 (в 32–256 раз) и связанную с ним «огранку» градиента, а внутренний цикл второго прохода упрощается.

Оценка памяти на 60 Мп при такой схеме: `L` уровня 1 для трёх каналов 180 МБ (размытие на месте), грубые уровни 60 МБ, рабочий буфер 60 МБ, полосы около 50 МБ — примерно 350 МБ.

### Б2. Обратная таблица по √L и порог «не изменился» 0.02 ступени несовместимы; для законных своих кривых ошибка доходит до 13 ступеней

**Раздел:** 5.4, 7 п. 1.

**Проблема.**
1. Требование точности таблицы — «< 0.1 ступени», а пиксель считается неизменённым при `|Δ| < 0.02` ступени. Любая ошибка таблицы в узле между 0.02 и 0.1 означает, что **все** неизменённые пиксели этого кода уходят в дизеринг и получают шум по всему кадру, в том числе на ровном поле.
2. Редактор разрешает почти горизонтальные участки («минимальный наклон ε»). На таком участке обратная кривая очень крутая, и равномерная по √L сетка её не держит. Запасной вариант из документа («узлы в точках кривой») не помогает: ошибка возникает между точками, а не в них.
3. Обращать сплайн вообще не нужно. Вход — 256 значений `LUT_in`; форма сплайна между соседними кодами ни на что не влияет, кроме произвольного результата дизеринга.

**Доказательство** (сплайн Fritsch–Carlson, таблица 4096 по √L с линейной интерполяцией, ошибка в узлах `LUT_in[c] → c`):

| Кривая | Макс. ошибка в узлах | Кодов с ошибкой > 0.02 |
|---|---|---|
| sRGB | 0.0000 | 0 |
| Скачок 254→255, всё ниже опущено в 10 раз | 0.013 (код 254) | 0 |
| То же, в 30 раз | 0.026 (код 254) | 1 |
| То же, в 100 раз | 0.034 (код 254) | 1 |
| Плато: (100; 0.2) → (150; 0.202) | 0.27 | 49 |
| Плато: (100; 0.2) → (150; 0.2002) | **13.2** | 52 |

Для последней кривой код 144 при нулевом ореоле превращается в 131 или 157.

Вторая, меньшая неточность того же места: `floor(v·255 + n)` смешивает соседние коды в пропорции по **закодированному** значению, а глаз и следующий расчёт усредняют **свет**. Для sRGB разница до 0.007 шага — пренебрежимо. Для скачка 254→255 среднее светового значения смещается на величину до 14 % шага (0.14 при доле 0.25), причём величина зависит от формы сплайна, которой пользователь не управляет.

**Предлагаемая замена первых двух пунктов 5.4:**

> - **Обратный перевод идёт по самой `LUT_in`, сплайн не обращается.** Для значения `v` ищется код `c`, для которого `LUT_in[c] ≤ v < LUT_in[c+1]`; поиск начинается с исходного кода пикселя и идёт соседними шагами. Дробная часть считается в линейном свете: `t = (v − LUT_in[c]) · R[c]`, где `R[c] = 1/(LUT_in[c+1] − LUT_in[c])` — таблица, посчитанная заранее. Квантование: `out = c + (t + n ≥ 1 ? 1 : 0)`, `v ≥ 1` → 255.
> - При построении `LUT_in` гарантируется строгое возрастание в float32: `LUT_in[c+1] > LUT_in[c]` для всех c (иначе редактор не принимает кривую).
> - **Пиксель не изменился**, если `|O_c − L_c| < 0.02 · (LUT_in[c+1] − LUT_in[c])` — сравнение в линейном свете, без участия обратного перевода. Тогда остаётся исходный код.

Свойства: узлы обращаются точно при любой кривой, «бит в бит при нулевом ореоле» получается по построению, нет `Math.sqrt` в пиксельном цикле (сейчас он нужен для индекса по √L и противоречит правилу 5.7 «нет вызовов функций»), исчезает задача «численное обращение сплайна».

Цена по замеру в `node --jitless`: второй проход на 24 Мп — 12.7 с с таблицей √L и до 16.8 с с поиском в худшем случае (случайная картинка, сдвиг на много кодов); на реальных снимках поиск делает 0–1 шаг.

Тест в 7 п. 1 «точность обратной таблицы < 0.1 ступени» заменить на: «для каждой из тестовых кривых (sRGB, скачок ×10 и ×100, плато с приращением 0.0002) все 256 кодов обращаются точно, и ровное поле любого кода при силе 100 остаётся неизменным бит в бит».

### Б3. Кэш предпросмотра в линейном свете устаревает при каждом изменении кривой

**Раздел:** 6.1 (предпросмотр), 5.6 п. 1, 10 п. 1.

**Проблема.** Уменьшенная копия строится усреднением **в линейном свете**, то есть уже после `LUT_in`. Документ обещает: «Ползунки к Photoshop не обращаются». Но в режиме 2 при любом движении точки кривой `LUT_in` меняется, а пересчитать усреднённые линейные значения под новую кривую нельзя. Остаются два варианта, и оба плохие:
- перечитывать весь документ полосами в модальном режиме на каждое изменение кривой (на 24 Мп по замеру около 2 с только на таблицу и усреднение, плюс чтение; на 60 Мп — около 5 с);
- применять новую кривую к старому кэшу — тогда предпросмотр расходится с результатом именно в том случае, ради которого сделана собственная пирамида (маленький источник 255 среди тёмного).

Основной рабочий приём Ильи по разделу 10 п. 1 — подбор высоты скачка 254→255. Он должен быть интерактивным.

**Доказательство.** Блок 12×12 исходных пикселей (масштаб 6000 → 500), из них 4 пикселя 255, остальные код 40. Кривая со скачком ×30. Истинное среднее света: `(4·1 + 140·0.00070)/144 = 0.0285`. Если усреднить в sRGB-линейном и потом перевести в новую кривую: среднее `(4 + 140·0.021)/144 = 0.048` → код 62 → `0.048/30 = 0.0016`. Ошибка энергии источника — в 18 раз.

**Предлагаемое изменение.** В 6.1 заменить пункт про копию на:

> - Кэш предпросмотра не зависит от кривой. На каждый пиксель копии и канал хранятся две величины: `f255` — доля исходных пикселей со значением 255, и `M` — среднее в sRGB-линейном свете по остальным пикселям блока. Свет для текущей кривой: `L = f255·1 + (1 − f255)·LUT_in[код(M)]`, где `код(M)` — обратный sRGB-перевод (дробный код, интерполяция по `LUT_in`).
> - Для источников (255) и для однородных блоков формула точна при любой кривой. Для остального она имеет ту же погрешность, что и пирамида Photoshop, но только внутри блока без источников.
> - Кэш перестраивается только по кнопке «Обновить» и при показе панели. Движение точек кривой, как и ползунков, к Photoshop не обращается.

И добавить тест в 7 п. 1: «результат предпросмотра и уменьшенный в линейном свете результат полного расчёта расходятся не больше чем на 3 % от пика ореола для набора: точечный источник 255, источник 3×3, ровное поле, кривая sRGB и скачок ×30».

## Существенные замечания

### С1. Цели по скорости в чистом JS недостижимы примерно вдвое

**Раздел:** 5.7, 4.

**Проблема.** «Применение на 24 Мп — не дольше 15 с» не выполняется даже для минимального второго прохода.

**Доказательство** (прототип, `node --jitless`, Apple M2 Pro, 6 Мп с пересчётом на 24 Мп):

| Этап | 24 Мп |
|---|---|
| Первый проход: `LUT_in` + усреднение 2×2 для трёх каналов | 1.9 с |
| Одна гауссиана (3 box-прохода, обе оси) на одном канале уровня 1 | 2.1 с |
| Второй проход, упрощённый до предела: один уровень `H`, увеличение ×2, обратная таблица, дизеринг, без альфы и проверок | 12.7 с |

Итого при схеме из Б1 (по одной гауссиане уровня 1 на канал, остальные на грубых уровнях): 1.9 + около 8 + 13…17 ≈ 23–27 с без учёта `getPixels` / `putPixels`. На 60 Мп — 60–70 с. Машина Ильи может быть медленнее M2 Pro.

Предпросмотр: 500×333 px = 167 тыс. пикселей. Сборка результата — около 90 мс, каждая гауссиана на полной сетке копии — около 57 мс на канал. В бюджет 300 мс помещаются 3–4 такие гауссианы; при правиле из документа их около 10.

**Предлагаемое изменение.** В 5.7 заменить цели на:

> - предпросмотр (длинная сторона 500 px, из кэша) — не дольше 500 мс на пересчёт; пересчёт запускается по последнему значению ползунка после паузы 100 мс, а не «раз за кадр»;
> - ядро на 24 Мп — не дольше 30 с; на 60 Мп — не дольше 80 с (`node --jitless`, Apple M2 Pro, без чтения и записи Photoshop);
> - 60 Мп — пик памяти ядра не больше 400 МБ.

Если 30 с на 24 Мп неприемлемы, решение о WebAssembly нужно принимать до начала разработки, а не после (см. раздел «Для пользователя»).

### С2. Box-фильтр из трёх проходов: ошибка σ до 9 % и квадратный ореол на больших расстояниях

**Раздел:** 5.3, 5.6 п. 2, 7 п. 1.

**Проблема.**
1. Целые ширины окон. При σ от 2 до 4 px (а правило уровней держит σ именно в этом диапазоне) фактическая σ отличается от заданной до −8.7 % (дисперсия −16.7 %; худший случай σ = 2.00 → окна 3, 3, 5). Один и тот же ореол на 12 и 60 Мп попадает на разные уровни с разной ошибкой квантования, то есть независимость от разрешения нарушается на уровне нескольких процентов радиуса ещё до всех остальных погрешностей.
2. Анизотропия. Три box-прохода дают квадратичный B-сплайн с квадратным носителем ±3σ. Составное ядро на расстоянии 15λ₁ (уровень 6·10⁻⁴ от пика): вдоль оси 0.63 от идеала, по диагонали 1.05. На 24–26λ₁: вдоль оси 0.72–0.23, по диагонали 1.47–1.52. Ореол получается квадратным с разницей радиуса изолинии около 11 %.
3. В режиме sRGB это ниже порога видимости. Но со своей кривой (скачок ×30…×100) источник в десятки раз ярче белого, и уровень 10⁻⁴ от пика — это видимые коды в тенях.

Четыре и пять проходов помогают мало (на 15λ₁: 0.76 и 0.81 против 1.00 и 0.97).

**Предлагаемое изменение.** В 5.6 добавить:

> - Две самые широкие гауссианы каждой экспоненты считаются настоящим гауссовым ядром (раздельная свёртка, радиус ⌈3.5σ⌉) — они лежат на грубых уровнях, где это дёшево. Box-проходы допустимы только для гауссиан, чьи хвосты перекрыты более широкими.
> - Для box-проходов используется фактическая σ набора окон: веса αᵢ и уровни подбираются под неё, либо применяется box с дробной шириной (взвешенные крайние отсчёты).

В 7 п. 1 добавить тест импульсного отклика всего конвейера: второй момент в пределах 3 % от `6·λ²·(0.6 + 0.4·3.3²)`; отношение значения вдоль оси к значению по диагонали в пределах ±15 % на всех радиусах, где ядро выше 10⁻⁴ от пика.

### С3. Радиусы каналов 1 / 0.55 / 0.35 обоснованы источником, который пользователь эталоном не считает, и расходятся с физичными моделями

**Раздел:** 5.3, 9, приложение («как у Dehancer и Resolve»).

**Проблема.**
1. Обоснование в приложении ссылается на Dehancer, хотя раздел 3 запрещает использовать его как эталон.
2. Физичные модели из исследования говорят другое. В spektrafilm σ одна на все каналы. У thatcherfreeman порядок обратный: R < G < B (3.0 / 3.2 / 3.3 ‰) — зелёный слой дальше от подложки, путь отражённого света длиннее, пятно не может быть уже. Соотношение 1 / 0.55 / 0.35 взято из PixelCraft, у которого работа идёт от порога.
3. Сам документ объясняет оранжевое ядро насыщением красного слоя. В режиме 2 со скачком 254→255 это насыщение воспроизводится само: красный канал ореола первым упирается в 255, зелёный продолжает расти, ядро становится оранжево-жёлтым. Узкое зелёное ядро поверх этого учитывает эффект дважды.
4. Цена: из-за разных радиусов самые мелкие гауссианы G и B попадают на уровень 0 (см. Б1), и ни одна гауссиана не делит уровень с другим каналом.

**Предлагаемое изменение.** В 5.3 заменить пункт «Радиусы по каналам» на:

> - **Радиусы по каналам:** по умолчанию `r = (1, 1, 1)`, как в spektrafilm. Оранжевое ядро и красный хвост получаются из соотношения `g_c` и из насыщения красного канала на выходе. Массив `r` остаётся константой ядра: вариант (1, 0.55, 0.35) сравнивается с базовым на демо-странице, и решение о значении по умолчанию принимает пользователь по картинкам.

В приложении убрать «как у Dehancer».

### С4. Чтение полосами: обрезка границ происходит в каждой полосе отдельно, а формула для прозрачности не дописана

**Раздел:** 5.5, 5.6, 6.3, 7 п. 2.

**Проблема.**
1. `getPixels` обрезает пустые области в **каждом** вызове. Для слоя с прозрачными краями полосы вернутся с разными `left` и `width`, а полностью прозрачная полоса — пустой или с ошибкой. Документ говорит только про один общий `sourceBounds`. Сценарий сбоя: вырезанный объект на прозрачном фоне — полосы результата смещены по горизонтали относительно друг друга.
2. Число компонент (3 или 4) нужно читать у каждого `imageData`, а не предполагать.
3. «Свет считается как `цвет × альфа`, а альфа результата равна исходной» — не сказано, делится ли результат обратно на альфу. Если нет — полупрозрачные края темнеют дважды (тёмная кайма, анти-цель). Если да — деление на ноль при α = 0 и значения больше 1 при малой α.
4. «Длинная сторона кадра» для `λ₁` не определена для слоя меньше документа.

**Предлагаемая замена 5.5:**

> - Рабочая область — пересечение границ слоя (`boundsNoEffects`) с документом; определяется один раз. Каждая полоса запрашивается по этой области, а возвращённые данные раскладываются в буфер полосы по **возвращённому** `sourceBounds`; всё, что не вернулось, считается прозрачным (α = 0, свет 0). Пустая полоса — не ошибка.
> - Источник ореола: `S_c = L_c · α`. Результат: `O_c = (L_c + a_c·(K_c ⊛ S)_c)/(1 + a_c)` для самого цвета (без умножения и деления на α), альфа копируется из исходной. При α = 0 пиксель копируется как есть.
> - `λ₁` считается от длинной стороны **документа**, а не слоя.
> - Число компонент берётся из каждого `imageData.components`.

В 7 п. 2 добавить случаи: слой со смещением (−30, +50), слой с прозрачной полосой посередине, слой меньше документа, изображения 1×N, N×1, 1×1 и 3×3, высота полосы 1, 7 и 512 дают одинаковый результат бит в бит.

### С5. Автоматическая перестройка предпросмотра при смене слоя блокирует Photoshop

**Раздел:** 6.1 («при открытии панели, смене документа или слоя»).

**Проблема.** Копия строится чтением **всего** документа полосами в модальном режиме: на 24 Мп около 2 с расчёта плюс чтение, на 60 Мп около 5 с и больше. Если это запускается при каждом щелчке по слою, Photoshop показывает окно прогресса и не даёт работать, пока открыта панель. Кроме того, модальный режим может быть занят (трансформация, другой плагин) — тогда фоновая перестройка даёт ошибку без действия пользователя.

**Предлагаемое изменение.** Заменить на: «Копия строится при показе панели и по кнопке „Обновить“. При смене документа или слоя панель только помечает предпросмотр как устаревший (подпись и выделенная кнопка „Обновить“) и к Photoshop не обращается. „Применить“ всегда читает актуальные пиксели».

### С6. После применения активным становится слой «Halation», и повторное применение ложится поверх результата

**Раздел:** 6.2.

**Проблема.** `createPixelLayer` делает новый слой активным. Типичный сценарий: применить, посмотреть, поправить ползунок, применить ещё раз. Второе применение берёт источником уже слой с ореолом — эффект удваивается, а пользователь этого не заказывал.

**Предлагаемое изменение.** Добавить в 6.2: «Перед выходом из модального режима активным снова делается исходный слой. В настройках сессии запоминается пара (ID исходного слоя, ID созданного слоя). Если при следующем применении активен созданный плагином слой, источником берётся его исходный слой, а пользователю предлагается заменить прежний результат».

Туда же, в 6.3: «Если у исходного слоя есть маска, непрозрачность ниже 100 %, режим наложения не „Обычный“ или он обтравочный — предупреждение и предложение применить к видимому изображению». Причина: новый слой с полным изображением такую маску или режим не унаследует и откроет скрытые области.

### С7. Отмена и отзывчивость: точки `await` нужны не только между полосами

**Раздел:** 5.6 п. 5.

**Проблема.** По замеру полоса 512 строк шириной 6000 px во втором проходе считается около 1.6 с, шириной 9500 px — около 2.6 с. Этап размытия между проходами (8–20 с на 24–60 Мп) в документе вообще не имеет точек отмены. Отмена сработает с задержкой до десятков секунд — это анти-цель «зависает без возможности отмены».

**Предлагаемое изменение.** Заменить п. 5 на: «Высота полосы подбирается так, чтобы в полосе было не больше ~1 Мп (расчёт не дольше ~0.6 с). `await`, проверка `isCancelled` и `reportProgress` выполняются между полосами, а на этапе размытия — после каждого прохода фильтра по каждому каналу. Прогресс распределён по замеренным долям этапов: чтение 10 %, размытие 35 %, запись 55 %».

### С8. Набор тестов не ловит главные риски

**Раздел:** 7.

**Проблема и предлагаемые добавления в 7 п. 1** (каждый пункт закрывает конкретный сценарий сбоя):

- **Сдвиг ореола на полпикселя уровня** — классическая ошибка пирамиды при несогласованных центрах пикселей. Тест: центр масс импульсного отклика совпадает с положением источника с точностью 0.25 px при размерах, не кратных степени двойки (например, 6001×3999).
- **Независимость от разрешения, допуск 15 %** — слишком слабо и не сказано, что сравнивается. Заменить на: результат 2048 px, уменьшенный в линейном свете до 512, отличается от результата 512 px не больше чем на 5 % от пика ореола.
- **«При силе 0 выход бит в бит равен входу»** проверяет только быстрый выход. Добавить: при силе 100 ровное поле каждого из 256 кодов остаётся неизменным в обоих режимах (ловит и переполнение `Uint8Array`: 256 превращается в 0, то есть чёрная точка в источнике света).
- **Дизеринг:** шум берётся по абсолютным координатам документа, результат не зависит от разбиения на полосы и от смещения слоя; среднее по тайлу значение `n` равно 0.5.
- **Свой цвет:** чёрный (0, 0, 0) не даёт NaN; чистый синий даёт R-вклад 0.
- **Память:** на 60 Мп в Node пик `process.memoryUsage().arrayBuffers` не выше цели.
- **Изотропия и второй момент ядра** — см. С2. **Предпросмотр против полного расчёта** — см. Б3.

В чек-лист для Photoshop (7 п. 6) добавить: «на 100 % в режиме „Разница“ между слоем результата и исходным нет горизонтальных швов на границах полос»; «слой со смещением и слой меньше документа»; «повторное применение»; «рост памяти Photoshop после трёх запусков на 60 Мп» с записью версии Photoshop (утечка `getData()` в 26.5).

## Мелкие замечания

### М1. Формулировки о физике нормировки неточны

**Раздел:** 5.2. «Светлая сторона чуть теряет энергию, которая и уходит в ореол» — физически неверно: отражённый свет уже прошёл эмульсию, первая экспозиция не уменьшается. Модель — это аддитивная halation `L + a·H` плюс постоянное поканальное усиление `1/(1 + a_c)` (баланс и экспозиция, откалиброванные на большом ровном поле). Следствие, которого в документе нет: у мелких ярких деталей и у края светлых объектов красный падает сильнее зелёного. При A = 0.25 у края белого объекта R уменьшается на 10 % в линейном свете (код 230 → 220), G — на 3 %: голубоватая кайма внутри светлого.

**Замена:** «Нормировка — это постоянное поканальное усиление `1/(1 + a_c)` поверх аддитивной модели: баланс и экспозиция откалиброваны на большом ровном поле вместе с его собственным рассеянным светом. Поэтому мелкие яркие детали и края светлых областей получают красного чуть меньше, чем середина большого поля (до `a_c/(2(1 + a_c))` у прямого края)». В 7 п. 4 добавить проверку на демо-странице: белый (230) квадрат на чёрном при максимальной силе — кайма внутри квадрата не должна бросаться в глаза; иначе снизить верхнюю границу A.

### М2. Ширина ядра по умолчанию не «соответствует σ = 65 мкм у spektrafilm»

**Раздел:** 5.3. λ экспоненты и σ гауссианы — разные меры. Ядро документа при λ₁ = 65 мкм: средний радиус 250 мкм, среднеквадратичный 354 мкм; половина энергии внутри 2.5λ₁ (0.45 % длинной стороны), 90 % — внутри 8.9λ₁ (1.6 %). У spektrafilm (три отскока, σ = 65 мкм): средний радиус 100 мкм, среднеквадратичный 115 мкм. Ядро по умолчанию в 2.5–3 раза шире spektrafilm и в 4–8 раз шире измерения ENS (плёнка с противоореольным слоем). Зато средний радиус близок к радиусу кольца полного внутреннего отражения 224–241 мкм для плёнки без противоореольного слоя.

**Замена:** «При 6000 px λ₁ ≈ 11 px. Половина энергии ядра лежит внутри 0.45 % длинной стороны, 90 % — внутри 1.6 %. Это в 2.5–3 раза шире значений spektrafilm для плёнки с противоореольным слоем и близко к масштабу ореола плёнки без него (CineStill, радиус кольца около 0.23 мм на кадре 35 мм)».

### М3. Сдвиг тайла по каналам делает шум цветным, а не наоборот

**Раздел:** 5.4. Одинаковый `n` для трёх каналов даёт нейтральный (яркостный) шум; сдвиг даёт независимый шум по каналам, то есть цветной. Сам выбор разумен (цветовой шум в 1 ступень менее заметен, чем яркостный), неверно только объяснение.

**Замена:** «Каналы берут тайл с фиксированными сдвигами (0, 0), (23, 37), (41, 11): шум каналов независим, и его яркостная составляющая меньше. Индекс тайла — по абсолютным координатам документа: `(x mod 64, y mod 64)`. Значения шума: `n = (ранг + 0.5)/4096`».

### М4. Цвет свечения: не описаны крайние случаи

**Раздел:** 5.2. Не сказано, какой кривой цвет переводится в линейный свет (должна быть всегда стандартная sRGB, независимо от режима), и что делать с чёрным цветом (максимум канала 0 → деление на ноль).

**Добавить:** «Цвет переводится стандартной кривой sRGB в обоих режимах. Если максимальный канал меньше 1/255, цвет не принимается и остаётся прежний».

### М5. Числовые поля точки кривой: не задана точность

**Раздел:** 5.1. Для скачка ×30 точка 254 имеет Y ≈ 0.033, а точки в тенях — порядка 10⁻⁴…10⁻⁵. Поле «Y (0–1)» с двумя-тремя знаками такие значения не вместит; на холсте с линейной осью вся кривая ниже скачка сольётся с нижней границей. Кроме того, чтобы «опустить всё ниже 255», пользователю придётся вручную двигать до 12 точек.

**Добавить:** «Поле Y принимает и показывает 6 значащих цифр. У холста есть переключатель оси Y: линейная / логарифмическая. Действие „Умножить все внутренние точки на коэффициент“ (числовое поле) — одна операция для подъёма источников над остальным изображением».

### М6. Аккумуляторы скользящей суммы — только в двойной точности

**Раздел:** 5.6 п. 2. Скользящая сумма box-фильтра во `Float32Array` накапливает ошибку после прохода через яркий источник (значение 1 рядом со значениями 10⁻⁵ при кривой со скачком) — горизонтальные и вертикальные следы от источников. **Добавить:** «Скользящие суммы хранятся в переменных или в `Float64Array`; в `Float32Array` записывается только результат».

### М7. Края кадра: уточнить для пирамиды

**Раздел:** 5.3, 5.6. При нечётных размерах уровня последний столбец и строка должны усредняться с повторением крайнего пикселя, а не с нулём; иначе у правого и нижнего края появится затемнение, и ровное поле перестанет быть неизменным. **Добавить** это правило одной строкой и тест «ровное поле 6001×3999 не меняется».

### М8. Утечка `getData()` и двойное чтение

**Раздел:** 5.6, 6.4. Исследование описывает утечку памяти размером с буфер на каждый `getData()` в Photoshop 26.5. Два прохода чтения на 60 Мп — это до 480 МБ утечки за одно применение. **Добавить в 6.4:** в отчёт диагностики — число вызовов `getPixels` и суммарный объём прочитанных данных; в 6.3 — предупреждение для версий 26.5–26.10: «в этой версии Photoshop возможен рост памяти при повторных запусках, перезапустите Photoshop при замедлении».

### М9. Режим «Только ореол» в предпросмотре

**Раздел:** 6.1. `a_c·H_c` включает и собственный свет пикселя, поэтому на ровном поле «только ореол» покажет не ноль, а `a_c·L_c`. Это не ошибка, но пользователь будет ждать картинку «свечение на чёрном». **Уточнить:** показывается `a_c·H_c/(1 + a_c)`, закодированное текущей кривой; в подписи — «весь рассеянный свет, включая возвращённый в ту же точку».

### М10. Точки кривой: минимальный шаг по X и значение ε

**Раздел:** 5.1. Не заданы минимальное расстояние между точками по X (должно быть не меньше одного кода) и величина ε. При схеме из Б2 достаточно условия строгого возрастания `LUT_in` в float32; **заменить** «минимальный наклон ε» на: «соседние точки отстоят по X не меньше чем на 1 код; после построения `LUT_in` проверяется `LUT_in[c+1] > LUT_in[c]` для всех c, иначе перемещение точки отклоняется».

## Для пользователя

Это не предложения изменить зафиксированные требования, а их следствия, о которых стоит знать заранее.

1. **Чистый JavaScript (требование 7) определяет скорость.** По замеру без JIT один только заключительный проход на 24 Мп занимает около 13 с на Apple M2 Pro, всё применение — 25–30 с, на 60 Мп — около минуты и больше. Цель «15 с на 24 Мп» из документа в чистом JS недостижима. Тот же расчёт на WebAssembly занял бы единицы секунд. Если полминуты на кадр Илью устраивает — менять ничего не нужно.

2. **«255 только у источников света» (требование 8) должно выполняться в каждом канале отдельно.** Модель поканальная. Насыщенный красный объект с R = 255 (платье, стоп-сигнал, неоновая вывеска) для красного канала — источник. При кривой со скачком 254→255 он даст такой же сильный красный ореол, как лампа. При подготовке файла нужно следить за значением 255 в любом из трёх каналов, а не только за белым.

3. **Без порога и в 8 битах режим sRGB почти не различает лампу и светлую стену:** свет кодов 255 и 250 различается на ~4 %. Заметно выделить источники можно только режимом 2 со скачком. Насколько источник ярче белого, плагин знать не может — эту величину Илья задаёт сам высотой скачка, и от неё зависит весь вид эффекта. Физически правдоподобный диапазон — от 4 до 100 раз.

4. **Результат в 8 битах обрезается на 255 жёстко.** Рядом с источником при сильном скачке красный канал ореола упирается в 255 раньше остальных, затем зелёный: переход красный → оранжевый → жёлтый → белый получается без плавного «плеча», как у плёнки. Это следствие 8-битного выхода без отдельной тональной кривой, а не ошибка расчёта.

5. **Дизеринг добавляет шум в 1 ступень везде, где ореол изменил пиксель хотя бы на 0.02 ступени** — в том числе на гладких участках далеко от источников. Это цена отсутствия полос. На чистых синтетических градиентах шум будет виден при сильном увеличении.
