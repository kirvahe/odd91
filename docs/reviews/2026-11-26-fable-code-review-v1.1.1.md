## Серьёзные

### С1. Тесты пропускают три мутации, которые портят результат: RGBA без порога, RGBA при разных радиусах, ширина не кратна 16

- **Где:** `test/core-v111.test.js:72–89` (`W = 640`, список `CASES`), `132–150` (тест пропуска), `tools/perf.mjs:22` (`W = 6240`).
- **Проблема.** Сам код в этих местах верен (см. «Проверено, замечаний нет»), но тесты его не держат:
  - обе ширины делятся на 16 (640 = 40·16, 6240 = 390·16), поэтому неполная последняя плитка сравнивается только сама с собой (тест высоты полосы в `core-v11.test.js`), а не с полным расчётом и не с v1.1.0;
  - RGBA в `CASES` один, с порогом и равными радиусами. Ветка `fineShared` при `NC = 3, comps = 4` (альфа без порога) и вся `finePlanar` с альфой с эталоном не сравниваются.
- **Свидетельство** (`mutate.js`: правка в копии, затем `node --test` по `core-v111`, `core-v11`, `core`, `bridge`). Из 18 мутаций 14 убиты, 4 выжили:

| Мутация | Что ломает | Итог |
|---|---|---|
| М15: `nT = floor(w / 16)` | Последние `w mod 16` столбцов остаются без мелкой части ореола | выжила |
| М17: в `fineShared` альфа умножается только при пороге | RGBA без порога: прозрачные пиксели светят как непрозрачные | выжила |
| М12: `finePlanar` не умножает на альфу | То же при разных радиусах каналов | выжила |
| М8: `codeAt` без цикла «вниз» | Ничего, кроме одного случая округления `sqrt` на границе интервала | выжила; мутация почти эквивалентна, см. ниже |

  Убиты: окно вертикали без первой или последней строки, расширение только влево, нулевые поля слева и справа, «грязный» `hor` в пустой строке и в пропущенной плитке, `codeAt` без цикла «вверх» и без обоих циклов, чужое ядро для канала веса, альфа в `fineShared` с порогом, сдвиг нижней строки контекста, дальний скачок вниз, незажатая правая граница плитки.

Цикл «вниз» — страховка на один шаг округления, тестом через `processImage` её не поймать. Замечания нет; достаточно комментария в коде, что цикл нужен только для этого.
- **Исправление.**
  - В тест пропуска и в сравнение с v1.1.0 добавить ширину, не кратную 16 (например 637×211), и ширину меньше одной плитки (15).
  - В `CASES` добавить два случая с `comps = 4`: без порога (`{ strength: 100, blurMul: 0.15 }`) и с разными радиусами (`radii: [1, 0.7, 1.4]`), лучше с неравномерной альфой.
  - Проверено `a-skip.js` и `d-rate.js`: настоящий код эти случаи проходит, тесты можно добавлять без правок ядра. На кадрах меньше 100 000 значений критерий «10⁻⁵ значений» надо заменить на «не больше одного значения»: на 33×90 RGBA одно отличие в 1 код — это уже 8,4·10⁻⁵.

### С3. Тест «отмена во время записи» отменяет после записи последней полосы

- **Где:** `test/bridge.test.js:290–311` (`["write", 0.999, 1]`).
- **Проблема.** Порог 0,999 достигается только последним сообщением прогресса (ровно 1). К этому моменту записаны все полосы. Тест по-прежнему проверяет откат и освобождение буферов, но не проверяет то, что обещает название: что отмена посреди записи останавливает цикл.
- **Свидетельство** (трассировка в копии теста). Сообщения прогресса: чтение до 0,083, размытие до 0,708, запись 0,735 … 1. При 0,999 — `putPixels` 10 из 10. При пороге 0,8 отмена приходит после 4 из 10 записей, при 0,72 — после первой; оба варианта проходят все проверки теста. Код отмены исправен: `checkpoint(ctx, stats)` бросает ошибку отмены так же, как раньше, счётчики уступок на это не влияют.
- **Исправление.** Взять порог 0,8 и добавить проверку `fake.log.putPixels.length < 10`. Чтобы тест не зависел от формулы оценки, порог можно считать от весов: `Bridge.stageWeights(core.createProcessor(...))`, середина этапа записи.

## Проверено, замечаний нет

**1. Мелкие гауссианы (`fineShared`, `finePlanar`)**
- Индексы: строки контекста `[R2 − r, nCtx − (R2 − r))` — ровно те, что читает вертикаль; поля по `R2` столбцов заполняются крайним пикселем; в `finePlanar` канал веса берёт ядро красного, как карта веса на базовой сетке; `fS / fC` в проходе 2 соответствуют обеим раскладкам.
- Буферы переиспользуются только как память: `out` обнуляется на длину полосы, `hor` в нужных строках каждой гауссианы пишется целиком. Результат не зависит от высоты полосы (тест есть; у меня полосы 1, 5, 13 строк и по умолчанию).
- Против v1.1.0 в обычном виде: не больше 1 кода, доля не выше 10⁻⁵ на всех кадрах 640×427 (`d-rate.js`), включая RGBA без порога и разные радиусы.

**2. Пропуск нулевых плиток**
- Расширение: `dt = ceil(r / 16)` плиток в обе стороны покрывает `r` пикселей; поля слева и справа повторяют пиксели плиток 0 и `nT − 1`, которые в расширение попадают (проверено неравенством и прогонами с яркими углами).
- Вертикаль: префиксные суммы `cnt` по строкам `[j0, j1]`, разность `cnt[ry + R2 + r + 1] − cnt[ry + R2 − r]` — ровно окно; размер `(nCtx + 1)·nT` достаточен; сдвиг начального значения на разность не влияет.
- Пропущенное место заполняется нулём, и полный расчёт даёт там тот же `+0` (все отводы положительны), поэтому `out += wt·0` ничего не меняет.
- Пустая строка (`rowNZ = 0`) обнуляет и `hor`, и `horT`; неполная последняя плитка зажимается по `w`; альфа входит в вес `k`, прозрачный пиксель с порогом — нулевой источник.
- Замер (`a-skip.js`): 3672 прогона, 0 расхождений с `_noSkip`. Размеры 637×211, 33×90, 17×40, 16×40, 15×33, 1×50, 250×3, 641×97, 1023×61; RGB и RGBA (в том числе случайная альфа); 6 наборов настроек с порогом; уровни 1, 2, 3; полосы 1, 5, 13 строк и по умолчанию.

**3. Развёрнутый проход 2**
- Без мелких гауссиан побитно равен v1.1.0 (тест есть; мутация дальнего скачка в синем канале убита). Вид «Только ореол» остался общим циклом и использует те же `fS / fC`.

**4. `codeAt`**
- Оба цикла вместе дают наибольший `k` с `lut[k] ≤ v` при любом начале, если таблица не убывает; начало влияет только на скорость. Старый поиск от исходного кода приходит туда же, потому что `lut[code]` лежит по ту же сторону от `O`.
- Замер (`b-codeat.js`): по 2 млн случайных пар на таблицу и крайние значения (`0`, `−0`, `1`, `1 − 2⁻⁵³`, `2⁻¹⁰⁷⁴`, `±Infinity`, `NaN`, точные квадраты `(i / 4096)²` с отклонением в последнем разряде) для sRGB, Reinhard с лимитами 1.01, 1.02, 1.0494, 1.1, 1.5, 4, трёх своих кривых и искусственной таблицы с повторами — 0 расхождений.
- Все таблицы, которые выдаёт `buildLutIn`, строго возрастают (свою кривую отсеивает `validateCurve`), `lut[255] = 1` во всех режимах, поэтому `v > lut[255]` сразу даёт 255. `NaN` до `codeAt` не доходит: обе ветки сравнения ложны, остаётся исходный код, как в v1.1.0.

**5. Связка и прогресс**
- Прогресс не убывает и кончается на 1 (тест есть); `stageWeights` возвращает прежние веса, если оценки нет, она бросает исключение или содержит ноль / `NaN` (`c-weights.js`).
- Оценка для кадра Ильи: чтение 519, размытие 487, запись 5399 мс — веса 0,08 / 0,08 / 0,84. С его прошлым отчётом (чтение 537, размытие 691 мс) и ожидаемой записью 5–6 с это сходится.
- `checkpoint(ctx, stats)`: без `stats` (предпросмотр, лупа) ведёт себя как раньше; отмена проверена на трёх порогах (С3).

**7. `npm run perf`**
