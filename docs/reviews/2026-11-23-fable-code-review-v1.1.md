## Серьёзные

### С1. Лупа считает на другом базовом уровне, чем «Применить», и при малом размытии показывает другой результат

- **Где:** `src/plugin/panel.js:930–935` (`renderLoupe` → `core.processImage` без `baseLevel`), `793–805` (`loupeReadRect`, выравнивание по 64 px), `src/core/processor.js:43–48` (`autoBaseLevel`).
- **Проблема.** Базовый уровень сетки выбирается по размеру обрабатываемой области. Для полного кадра 24 Мп это уровень 1, для 60 Мп — уровень 2. Фрагмент лупы меньше 1 Мп, поэтому он считается на уровне 0. Выравнивание чтения по 64 px («как блоки пирамиды при применении») при этом ничего не даёт: уровень другой, и узкие гауссианы считаются иначе. Приложение G и подсказка в панели называют лупу точным результатом.
- **Сценарий (воспроизведён, `loupe.js`).** Кадр 6000×4000, фон 60–66, белые квадраты и линии в центре, режим «8 бит → scene-linear», сила 100 %. Сравнивается окно лупы 278×278 с тем же местом полного `processImage`:

| Размытие | Запас, px | Уровень лупы / применения | Макс. расхождение, коды | Значений с расхождением > 3 |
|---|---|---|---|---|
| ×0.01 | 8 | 0 / 1 | 118 | 3340 |
| ×0.05 | 18 | 0 / 1 | 22 | 2120 |
| ×0.1 | 35 | 0 / 1 | 8 | 510 |
| ×0.25 | 87 | 0 / 1 | 3 | 0 |
| ×1 | 346 | 1 / 1 | 0 | 0 |

  Для 60 Мп (применение на уровне 2, эмуляция `loupe60.js`): ×0.25 — 11 кодов, ×0.1 — 20, ×0.05 — 45.
- **Исправление.** Передавать в лупу уровень полного применения:
  - экспортировать из ядра `baseLevelFor(width, height)` (это `processor.autoBaseLevel`);
  - в `renderLoupe` добавить в опции `baseLevel: core.baseLevelFor(rectW(plan.area), rectH(plan.area))`, где `plan = state.previewPlan`;
  - `LOUPE_ALIGN = 64` тогда действительно нужен: смещение фрагмента кратно 2^уровень до уровня 6.
  - Проверено: с этим параметром расхождение равно нулю во всех строках таблицы (и остаётся ≤ 1 кода при ×2 и ×4, где запас упирается в 1024 px).
  - Тест в `core-v11.test.js`: кадр больше 1 Мп, размытие ×0.05, фрагмент с запасом `loupeMargin` и `baseLevel` полного кадра совпадает с вырезкой из полного результата.

### С2. На кадрах больше 1 Мп размытие меньше примерно ×0.1 не становится уже: ядро ограничено шагом базовой сетки

- **Где:** `src/core/processor.js:32–41` (`baseGaussians`: `v = σ² − extra`, при `v ≤ 0` гауссиана становится дельтой на базовой сетке), `13` и `43–48` (уровень 0 только до 1 Мп), `src/core/halo.js:11, 23`.
- **Проблема.** Добавка дисперсии от пересчёта в базовую сетку и обратно равна 1,0 px² на уровне 1 и 4,0 px² на уровне 2. Гауссиана с σ меньше 1 px (уровень 1) или 2 px (уровень 2) заменяется дельтой, то есть фактически размывается самим пересчётом. При ×0.01 на кадре 6000 px λ = 0,108 px, и план размытия состоит из шести дельт: ядро целиком равно ядру пересчёта и от ползунка уже не зависит. Диапазон ×0.01…×0.1 — главное расширение версии 1.1.
- **Сценарий (воспроизведён, `floor.js`).** Кадр 6000×4000, фон 60, белые квадрат 40×40, линия 1 px и точка 3×3, sRGB, сила 100 %. Сравнивается результат применения (уровень 1) с точным ядром (тот же фрагмент на уровне 0):

| Размытие | План применения | Макс. расхождение с точным ядром, коды |
|---|---|---|
| ×0.01 | 6 дельт | 80 |
| ×0.03 | 4 дельты + 2 гауссианы | 38 |
| ×0.05 | 3 дельты + 3 гауссианы | 27 |
| ×0.1 | 1 дельта + 5 гауссиан | 10 |
| ×0.25 | — | 4 |

  Точное ядро при ×0.01 почти ничего не меняет, а применение рисует вдоль всех границ кайму шириной 1–2 px.
- **Исправление.**
  - Настоящее: гауссианы, у которых `v ≤ 0`, считать в полном разрешении внутри прохода 2 — короткой раздельной свёрткой по взвешенному источнику полосы. Радиус не больше 3σ, то есть 3–6 строк; полосы тогда читаются с таким нахлёстом. Базовой сетке остаются только широкие гауссианы.
  - Минимальное, пока этого нет: показывать под полем размытия подсказку, когда ядро упирается в сетку. Условие: `2.7684·λ ≤ 2^(b−1)`, где `λ = 0.0018·docLongSide·blurMul`, `b` — уровень применения. Для 6000 px это ×0.033 и меньше. Текст: «на этом документе размытие меньше ×N не различается».
  - Простая замена «дельты на базовой сетке» на «собственный свет пикселя» не помогает: проверено (`floor2.js`), при ×0.01 ошибка падает с 80 до 34, но при ×0.05 растёт с 27 до 40.
  - После исправления С1 лупа будет честно показывать то, что даёт применение, включая это ограничение.

### С3. Слой пользователя с именем «Halation …» считается результатом: удаляется при замене, подменяется соседним и выпадает из видимого изображения

- **Где:** `src/core/presets.js:125–127` (`/^Halation(\s|$|\s*\[)/`), `src/plugin/ps-bridge.js:462–466`, `488–506` (`resultLayersOf`), `509–517` (`resultsDirectlyAbove`), `529–537`, `804–813` (ветка «активен слой результата»), `860`, `1319–1328` (удаление).
- **Проблема.** Результатом считается любое имя, которое начинается со слова «Halation» и пробела. В версии 1.0 прежние результаты удалялись только по ID текущей сессии; теперь — ещё и по имени.
- **Сценарии (воспроизведены на поддельном Photoshop, `names.js`, `names2.js`).**
  1. Слои сверху вниз: «Halation mask paint» (ретушь пользователя), «Фото». Активен «Фото», галочка «Заменять прежний результат» включена (значение по умолчанию). После «Применить» `previousResultIds = [9]`, слой пользователя удалён, статус «Готово… Прежний результат удалён». То же для «Halation copy», «Halation 2», «Halation — ретушь».
  2. Пользователь назвал копию фотографии «Halation test» и сделал её активной. Панель пишет «Активен слой результата Halation — эффект будет применён к слою под ним «Фото»» и сразу запускает обработку: обработан другой слой, а активный удалён.
  3. Источник — видимое изображение. Слой «Halation ретушь» скрывается на время чтения: ни одно из чтений композита его не видит, эффект посчитан без него.
- **Исправление.** Узнавать по имени только то, что создаёт сам плагин:

```js
function isResultLayerName(name) {
  return typeof name === 'string' &&
    (name === 'Halation' || /^Halation(?: · [^\[\]]*)? \[h1:/.test(name));
}
```

  - Незакрытая скобка допускается намеренно: если Photoshop обрежет длинное имя, слой всё равно узнаётся.
  - Дубликат результата («… [h1:…] copy») проходит по началу имени; если это нежелательно, добавить в конец шаблона `[^\]]*\]$`.
  - Тесты: слой «Halation mask paint» над источником не попадает в `previousResultIds` и не скрывается при чтении композита; активный слой «Halation test» обрабатывается сам.

### С4. Порог: зерно и фактура с яркостью около порога превращаются в красную «крупу»

- **Где:** `src/core/settings.js:216–220` (`combine`: `E = H − w·L` с весом самого пикселя), `src/core/processor.js:245–248` и `254, 274, 294`, `src/core/preview.js:334`.
- **Проблема.** `H` усредняет веса соседей, а собственная доля берётся с весом самого пикселя. Пиксель чуть темнее порога (`w ≈ 0`) рядом с пикселями чуть светлее порога (`w ≈ 1`) получает `E ≈ H` целиком, хотя соседи почти той же яркости. Инвариантность строго ровного поля сохраняется (проверено на 2016 сочетаниях), но на настоящем кадре с шумом её нет.
- **Сценарий (воспроизведён, `grain.js`, `fixes.js`).** Поле 600×400, код 128 с шумом σ = 2 кода, sRGB, цвет по умолчанию, порог 128. Красный канал, среднее ± разброс (на входе 128,0 ± 2,0):

| Плавность | Сила | Сейчас | С исправлением ниже |
|---|---|---|---|
| 0 | 100 % | 140,8 ± 13,9 | 129,0 ± 1,2 |
| 8 | 100 % | 135,3 ± 7,8 | 128,8 ± 1,4 |
| 32 | 100 % | 130,6 ± 2,2 | 128,5 ± 1,5 |
| 32 | 400 % | 137,3 ± 11,2 | 130,0 ± 1,2 |

  На фотографии это участки неба, стен или кожи с яркостью около порога.
- **Исправление.** Сравнивать пришедший ореол с долей, взвешенной теми же соседями: `E_i = H_i − L_i·(K∗w)_i`, где `K∗w` — карта весов, размытая тем же ядром.
  - Ровное поле: `K∗w = w`, `E = 0`, как сейчас. Порог выключен: `K∗w = 1`, формула версии 1.0.
  - Тёмный пиксель рядом с лампой получает `m·(L_лампы − L)`, то есть ровно столько же, сколько без порога. Проверено: в 12 px от лампы на фоне 100 без порога 207,158,107; с порогом 200 сейчас 207,159,107; с исправлением 207,158,107.
  - Реализация: вторая базовая сетка `wbase`, в неё в проходе 1 копится тот же множитель `k = w·α`; та же нормировка блоков; второй запуск `haloForChannels` с теми же гауссианами; в проходе 2 `wl` берётся билинейной интерполяцией из размытой карты вместо веса пикселя. Только при `threshold > 0`. Цена: ещё одно размытие и `12·bw·bh` байт.
  - Проверено на копии ядра: ровные поля не меняются (180 сочетаний, обе модели, уровни 0–2).
  - В предпросмотре — то же с картой `wRest` / `w255`. Обновить формулу в `API.md` и в приложении G.
  - Если модель менять не хочется: ограничить плавность снизу (например, 16 при включённом пороге) и написать об этом в подсказке. Это ослабляет эффект, но не убирает: строка «32 / 400 %» в таблице.

### С5. Сила больше 100 % в модели «Без каймы»: тёплый сдвиг на зерне и инверсия тонких тёмных деталей

- **Где:** `src/core/settings.js:68–71` (`strengthToA`: a до 4), `src/core/processor.js:259, 279, 299` (`O = L + a·d` при `d > 0`), `src/core/settings.js:218`.
- **Проблема.** При `a > 1` выражение `L + a·(H − L)` убывает по `L`: чем темнее пиксель относительно окружения, тем ярче он становится, и в итоге он ярче окружения. Это не ошибка реализации, а свойство формулы: поточечная функция от `L` и `H`, которая не меняет ровное поле и даёт `a·H` на чёрном, при `a > 1` не может быть монотонной. Но диапазон 100–400 % добавлен именно в этой версии, и на любом кадре с зерном он нарушает обещание приложения D «общего тёплого сдвига нет».
- **Сценарии (воспроизведены, `grain.js`).**
  - Поле 128 с зерном σ = 6 кодов, sRGB, цвет по умолчанию. Красный канал: при 100 % — 130,5 ± 3,5; при 400 % — 137,1 ± 7,9 (сдвиг +9 кодов, зерно грубее исходного); зелёный 130,8. При σ = 2: 131,1 ± 3,0. В модели Proosa при 400 % сдвига нет (128,2 ± 1,3).
  - Тёмная линия шириной 1 px (код 40) на сером 150: при 100 % линия становится 149,88,45; при 200 % — 200,116,50; при 400 % — 255,156,59 при неизменном фоне 150,150,150. Тонкая тёмная деталь светится ярче фона.
- **Исправление** (решение по модели — за автором и пользователем):
  - Вариант 1: выше `a = 1` наращивать добавку квадратично по относительному избытку: при `a_c > 1` и `d > 0` считать `O = L + d·(1 + (a_c − 1)·d/H)`. На чёрном рядом с лампой `d ≈ H`, добавка равна `a·H`, как сейчас. На зерне `d/H` — несколько процентов, и поведение остаётся как при 100 %. Проверено (`fixes.js`): зерно σ = 6 при 400 % — 131,4 ± 3,3 вместо 137,1 ± 7,9; в 12 px от лампы на фоне 20 — 180,103,35 против 183,104,35.
  - Вариант 2: оставить формулу и показывать при силе больше 100 % подсказку: «выше 100 % усиливается зерно и тонкие тёмные детали у светлого становятся оранжевыми; включите порог». С порогом 200 зерно в полутонах не меняется вовсе (128,0 ± 6,0).

### С6. Предпросмотр «Кадр» с порогом: часть блока со значением 255 всегда считается белой

- **Где:** `src/core/preview.js:268` (`w255 = lumaWeight(phys, 1)`), `278`, `341`.
- **Проблема.** В кэше канал со значением 255 хранится отдельно, и при пороге ему даётся вес белого. В ядре вес берётся по яркости всего пикселя: у насыщенного красного (255, 30, 20) она соответствует коду около 127. Приложение G оговаривает приближение «по средней яркости блока», но здесь ошибка систематическая и качественная.
- **Сценарий (воспроизведён, `prev.js`).** Кадр 3000×2000, фон 40, красная лампа 40×40 (255, 30, 20), образ «Только лампы» (порог 235). В 20 px от лампы: предпросмотр 199,40,40; полный результат 40,40,40. Вокруг стоп-сигналов и неоновых вывесок кадр показывает сильный ореол, которого применение не даст.
- **Исправление.** Хранить в кэше яркость пикселей со значением 255:
  - в `push`: если канал `c` равен 255, копить `lum255[b3 + c] += a·Y`, где `Y` — линейная яркость пикселя по sRGB;
  - в `finish`: `lum255 / c255`; в `downscaleProxy` — среднее с весом `f255`;
  - в `previewFields` и `renderPreview`: `w255` для блока и канала равен `lumaWeight(phys, lum255[j])`.
  - Кэш по-прежнему не зависит от настроек. Белая лампа 60×60 сейчас сходится с полным результатом до 3 кодов и так и останется.
- **Заодно, как известное ограничение.** Тонкая светлая деталь без значения 255 (линия 3 px, код 245) с порогом 235 в кадре не даёт ореола совсем: предпросмотр 40,40,40 против 96,57,42. Это заявленное приближение, лупа показывает верно. Улучшить можно гистограммой яркости блока на 6–8 интервалов; это необязательно.
- **Замечание по смыслу порога.** Порог по яркости Rec.709 исключает насыщенные красные и оранжевые источники: вес (255, 30, 20) равен нулю уже при пороге 235. На плёнке именно они дают самый сильный ореол. Если это не задумано, считать вес по `max(R, G, B)`; минимум — написать об этом в подсказке к порогу.

### С7. Встроенный образ и «Взять настройки из слоя» стирают подобранную кривую

- **Где:** `src/plugin/panel.js:1074–1083` (`loadSettings`), `1085–1092`, `1462–1465`; `src/core/presets.js:12–30` (у образов нет `curvePoints`), `91` (`settingsFromToken` возвращает нормализованные настройки).
- **Проблема.** `normalizeSettings` подставляет кривую по умолчанию, когда `curvePoints` не задан. Все встроенные образы работают в режимах sRGB и «8 бит → scene-linear», то есть кривая им не нужна, но загрузка образа заменяет точки пользователя, а `scheduleSave` тут же записывает это в `localStorage`. То же при загрузке из слоя, сделанного не в режиме кривой: в токене нет поля `k=`.
- **Сценарий.** Режим «Своя кривая», 12 точек подобраны вручную. Пользователь выбирает «CineStill 800T» и нажимает «Загрузить», смотрит, возвращается в режим «Своя кривая» — там кривая sRGB. Отмены в панели нет. Потерянная кривая — одна из исходных жалоб Ильи.
- **Исправление.** В `loadSettings` сохранять текущие точки, если загружаемые настройки их не несут:
  - для встроенного образа (`p.builtIn`) и для настроек из слоя с `mode !== "curve"` перед `normalizeSettings` подставлять `curvePoints: state.settings.curvePoints`;
  - свои пресеты загружать как сейчас: они хранят кривую намеренно.
  - Тест в `panel-smoke.test.js`: задать кривую, загрузить `look:cinestill-800t`, проверить, что `state.settings.curvePoints` не изменились.

## Мелкие

### М1. Лупа: любая ошибка `getPixels` в режиме слоя превращается в пустую клетчатую область

- **Где:** `src/plugin/ps-bridge.js:1250` (`tolerate: plan.mode === "layer"`), `1251–1259`.
- **Проблема.** Это тот же класс, что прежнее С5: ошибка чтения молча считается прозрачной областью. Для лупы нет ни проверки по границам слоя, ни предупреждения.
- **Сценарий.** Предпросмотр построен по слою, затем слой удалён или объединён (метка «устарел» видна). Щелчок по кадру: `getPixels` с прежним `layerID` даёт ошибку, лупа показывает «шахматку» без сообщения.
- **Исправление.** Если `s.tolerated`, возвращать в `region` поле `warning` с текстом ошибки, а в `renderLoupe` выводить его в `preview-source`: «Photoshop не отдал пиксели этой области: она прозрачна или слой изменился — нажмите «Обновить»».

### М2. Маска по выделению: чтение выделения в самом конце, пустой ответ даёт невидимый результат

- **Где:** `src/plugin/ps-bridge.js:1409–1413` (вызов после прохода 2), `1150–1180`, `1154–1156`.
- **Проблемы и сценарии.**
  - Выделение читается после всей обработки. Если `getSelection` бросит исключение (выделение снято между проверкой и применением, версия без метода), вся работа откатывается через десятки секунд. Наличие методов проверяется там же, в конце.
  - Если `getSelection` вернул ответ без `imageData`, маска остаётся чёрной: слой результата невидим, а статус — «Готово… Маска слоя — по выделению». То же, когда выделение не пересекает область слоя (тест `bridge.test.js:746` закрепляет это как норму).
  - Документация Adobe не говорит, какого размера `imageData` при заданном `sourceBounds` и что тогда лежит в возвращённом `sourceBounds`. Код берёт левый верхний угол из ответа. Если Photoshop отдаёт данные размером с запрошенную область, а `sourceBounds` — границы выделения, маска сместится.
- **Исправление.**
  - Читать выделение в начале, сразу после `suspendHistory`: собрать буфер маски, проверить методы; `putLayerMask` оставить в конце.
  - Если в маске нет ни одного ненулевого значения — бросать `nothingToDoError("Выделение не пересекает обрабатываемую область…")` до чтения пикселей.
  - Если `imageData.width === W` и `imageData.height === H`, считать, что данные покрывают `area`, независимо от возвращённых границ.

### М3. Порог рядом с 255 при ненулевой плавности ослабляет даже белый

- **Где:** `src/core/settings.js:149–158`.
- **Сценарий (проверено, `det.js`).** Плавность 32 (значение по умолчанию): при пороге 245 вес белого 0,91; при 250 — 0,73; при 255 — 0,50. Пользователь поднимает порог, чтобы оставить только лампы, и ореол самих ламп падает вдвое.
- **Исправление.** Сдвигать окно так, чтобы оно не выходило за 255: `e1 = Math.min(255, threshold + softness/2); e0 = e1 − softness`.

### М4. Редактор кривой: отложенная отрисовка может не состояться, а `resize()` больше не перерисовывает

- **Где:** `src/plugin/curve-editor.js:397–405` (`render`), `267–283` (`resize`), `src/plugin/panel.js:313`, `1610`.
- **Проблема.** `render()` ставит флаг `_frameQueued` и ждёт `requestAnimationFrame`. Если UXP не вызывает обратный вызов для скрытой панели или отбрасывает его, флаг остаётся поднятым и все следующие `render()` ничего не делают. Раньше страховкой был `resize()` при показе панели и при входе в режим кривой; теперь при неизменном размере он возвращает `false` и не рисует. Проверить поведение `requestAnimationFrame` в UXP без Photoshop нельзя.
- **Сценарий (предположительный).** Смена темы или загрузка пресета, пока панель скрыта; после показа кривая остаётся прежней или пустой до изменения ширины панели.
- **Исправление.**
  - В `render()` запоминать время постановки и при ожидании дольше 250 мс рисовать заново: `if (this._frameQueued && nowMs() − this._queuedAt < 250) return;`
  - В `renderNow()` сбрасывать `_frameQueued`.
  - В `panel.js` (`onShow`, `renderMode`): `if (!state.editor.resize()) state.editor.render();`

### М5. Лупа: устаревшее состояние и пропущенный пересчёт

- **Где:** `src/plugin/panel.js:683–694`, `879`, `891`, `881, 884, 899`.
- **Проблемы и сценарии.**
  - При блокирующей проверке или пустом слое `state.proxy` обнуляется, а `state.previewPlan` и `state.loupe.raw` остаются. Документ перевели в 16 бит: в области предпросмотра сообщение об ошибке, но любое движение ползунка в режиме «Лупа» снова рисует фрагмент прежнего документа поверх него.
  - `readLoupe` возвращает `false`, когда панель занята, и `updateLoupe` молча выходит. Настройка изменена во время применения: лупа остаётся с прежними настройками до следующего изменения.
  - `state.loupe.needsRead` только записывается и нигде не читается.
- **Исправление.** В ветках `rep.blocking.length` и `rep.nothingToDo` обнулять `previewPlan` и `loupe.raw`. В `setBusy(false)` вызывать `updateLoupe(true)`, если стоит `needsRead`; поднимать этот флаг и при отказе из-за занятости.

### М6. «Лупа 1:1» на экране Retina — это 200 % в терминах Photoshop

- **Где:** `src/plugin/panel.js:773–784`, `823–848`, `951`.
- **Проблема.** Картинка лупы выводится пиксель в пиксель CSS. По `best-practices.md` (§4.2) `window.devicePixelRatio` в UXP всегда равен 1, поэтому на Retina один пиксель документа занимает 2×2 пикселя экрана и сглаживается при увеличении. Пользователь, сравнивающий лупу с окном Photoshop при 100 %, видит другую резкость и вдвое меньшее поле.
- **Исправление.** Добавить масштаб «½»: область `2·box` пикселей документа, картинка в полном размере, элемент `img` размером `box`. В подсказке написать, что на Retina это соответствует 100 % в Photoshop. Проверить у Ильи, как UXP уменьшает картинку.

### М7. Разбор токена и нормализация: тихие подстановки

- **Где:** `src/core/presets.js:87–91`, `src/core/settings.js:118`.
- **Сценарии.**
  - Токен с `m=c` и испорченным или отсутствующим `k=` (имя слоя правили руками): `settingsFromLayerName` возвращает режим «кривая» с кривой по умолчанию, и «Взять настройки из слоя» молча даёт не ту кривую. Нужно возвращать `null`, если `m=c`, а `validateCurve(out.curvePoints).ok` ложно.
  - `normalizeSettings({ blurMul: null })` даёт 0,01, а не 1: `Number(null) === 0` считается конечным числом. То же для пустой строки и `false`. В условие стоит добавить `typeof s.blurMul === "number"` или разбор строки с проверкой на пустоту.
- С кривыми из редактора (целые X) токен надёжен: см. «Проверено».

### М8. `API.md`: верхний блок настроек описывает версию 1.0

- **Где:** `src/core/API.md:12–21`.
- **Проблема.** В основном блоке остались `blur: 50` со шкалой 0..100 и «`A = 0.25 * strength/100`», нет `model`, `reinhardLimit`, режима `reinhard`. Раздел «v1.1 additions» этому противоречит. Файл назван контрактом ядра.
- **Исправление.** Переписать блок по `DEFAULTS` из `settings.js`, старые поля оставить одной строкой как принимаемые для совместимости.

### Пробелы в тестах

- Лупа сравнивается с полным расчётом только на кадрах, где уровни совпадают (С1).
- Нет теста на слой пользователя с именем «Halation …» (С3).
- Инвариантность проверяется только на строго ровных полях; нет поля с шумом около порога (С4) и при силе больше 100 % (С5).

## Риски, которые нельзя проверить без Photoshop

1. `putLayerMask` на слое без маски: по тексту документации при `replace: true` маска создаётся, но примера нет.
2. Ответ `getSelection`, когда выделения нет или оно вне `sourceBounds`: исключение, пустой ответ или нули.
3. Влияет ли активное выделение на `putPixels`. Если запись обрезается выделением, слой результата окажется обрезанным ещё до маски.
4. Длина имени слоя: принимает ли Photoshop 255 символов с кириллицей и знаками «·», «×» без обрезки.
5. `sp-slider` с `step="0.1"`: атрибута нет в списке из `best-practices.md` (§4.1). Если ползунок отдаёт только целые, шаг размытия будет около 6 %; точное значение доступно через поле.
6. `sp-picker` с пунктами, созданными из кода: откуда брать выбранное значение (`value`, `selectedIndex`, `selected`). Код пробует все три.
7. `requestAnimationFrame` для скрытой панели (М4), свойство `outline` в CSS у рамки лупы, `clientWidth` у `preview-wrap`.
8. Мерцание редактора кривой: исправление выглядит разумно, но причина в коде не доказана; подтвердить может только Илья.

## Проверено, замечаний нет

**Ядро**
- Формула `E = H − w·L` одинакова в `settings.combine`, в цикле `pass2`, в виде «Только ореол» и в предпросмотре. Proosa без порога алгебраически равна `(L + a·H)/(1 + a)`.
- Строго ровные поля не меняются: 2016 сочетаний (обе модели; порог 0, 1, 50, 128, 200, 255; плавность 0, 1, 32, 255; уровни 0–2; sRGB и scene-linear; сила 400 %; три разных кода в каналах).
- Результат не зависит от высоты полосы при включённом пороге, в обоих видах, для RGB и RGBA: 360 прогонов, полосы 1, 3, 7 строк, размеры 37×53, 64×64, 1×40, 40×1, 101×7. Альфа не меняется, пиксели с α = 0 копируются как есть.
- Таблица весов: 4096 интервалов по линейной яркости, индекс белого не выходит за границу; плавность 0 даёт ступеньку; порог 0 возвращает `null` и прежние ветки кода.
- `strengthToA` непрерывна в точке 100 % (0,09 при 30; 1 при 100; 4 при 400; выше 400 ограничивается). Шкала размытия: 0 → ×0.01, 100 → ×4, ×1 на 76,87. Старое поле `blur` 0 / 50 / 100 переводится в ×0.25 / ×1 / ×4.
- Вид «Только ореол» в `processImage` кодируется через ту же кривую, что и в предпросмотре; при силе 0 даёт чёрное, а не копию.
- Токен в имени слоя: 30 000 кривых, какие выдаёт редактор (целые X, 10–12 точек, умножение на k от 0,001 до 1, скачок у 253–254), все читаются обратно; относительное расхождение таблицы не больше 2,3·10⁻⁵; имя не длиннее 255 символов; при нехватке места сначала убирается сводка, затем снижается точность Y. Токен без `m=`, мусор и дубликат с « copy» дают `null`.
- Запас лупы: 346 px для 6000 px при ×1, ограничение 1024 px. При ×2 и ×4 расхождение лупы с полным расчётом не больше 1 кода (кадр с лампами по всей площади, сила 100 и 400 %).
- Геометрия лупы: вырезка из кэша, смещения, начало координат шума, прижатие окна к краям области. При равном базовом уровне фрагмент совпадает с полным результатом бит в бит.

**Связка с Photoshop**
- Параметры `getSelection`, `putLayerMask` и `createImageDataFromBuffer` для маски соответствуют `imaging.md`: один компонент, `Grayscale`, `Gray Gamma 2.2`, `targetBounds` из `left` и `top`. Маска пишется в том же шаге истории. `dispose()` для данных выделения и маски стоит в `finally`.
- `readSelectionBounds`: `Document.selection.bounds` со значением `null`, запасной путь через `batchPlay` со значениями в единицах, исключение считается отсутствием выделения.
- `readRegion`: один `executeAsModal`; прямоугольник прижимается к области; возвращается собственная копия буфера; в режиме видимого изображения результаты скрываются внутри приостановленной истории, которая затем отбрасывается; флаг занятости ставится до первого `await`.
- `putPixels` по-прежнему с `replace: false`; порядок слоёв, удаление прежних результатов и повторный выбор источника не изменились.
- Имя слоя результата обрезается до 255 символов и попадает в диагностику.

**Панель**
- Перенос настроек версии 1.0: запись со схемой 1 читается, `blur` переводится в `blurMul`, сила сохраняет смысл (квадратичная шкала до 100 %), запись сразу пересохраняется со схемой 2; неизвестная схема и испорченный JSON дают значения по умолчанию.
- Пресеты: перезапись по имени без учёта регистра, предел 100, длина имени 60, испорченное хранилище даёт пустой список, встроенные образы нельзя удалить.
- Числовые поля: запятая как разделитель, знаки «×» и «%», ограничение диапазоном с сообщением, нечисловой ввод возвращает прежнее значение.
- Кэш лупы сбрасывается при «Обновить» и при новом центре; чтение из Photoshop происходит только при нехватке запаса; при перетаскивании ползунка лупа считается по имеющемуся кэшу.
- Редактор кривой: при неизменном размере холст не очищается, несколько `render()` за кадр дают одну отрисовку, подписи осей пересоздаются только при смене оси или размера; изменения ширины окна меньше 8 px игнорируются без накопления ошибки.

**Сборка**
- `.ccx` собирается, версии в `package.json`, манифесте, `panel.js` и ядре совпадают (1.1.0).
